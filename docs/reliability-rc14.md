# Reliability candidate 0.5.0rc14

This candidate adds local safeguards. Stable release still requires independently verified employer acceptance for each claimed capability, an actual scheduled cycle on the installed revision, current Gmail authorization, and an encrypted off-device backup with an independent restore. Synthetic results do not establish these gates.

## Preparation and native writes

The browser builds an immutable application specification from the inspected questions, native identities, choices, validation rules, declared conditional dependencies, required documents and approved answer provenance. Existing answer resolution supplies facts; unknown personal, eligibility, legal and demographic answers remain unanswered. Ashby, Greenhouse and Lever retain their individual guarded transports and post-fill verification. DOM filling and an HTTP success never confirm an application.

Every visible control and every approved document is validated before file selection. Ashby additionally compiles its official render, definition, field paths and native answer encodings without enabling autosaves. Attachment targets are inspected before the first upload. Changed source data or native metadata stops further writes. A conditional reveal needs another inspection and approval pass in the same session; an unsupported reveal produces a hold.

Ashby operations have a separate durable journal for field saves, texting consent, upload-handle creation, binary upload and native attachment. Intent must commit before transport. An operation-specific validated acknowledgement must commit before in-memory success. Binary storage acknowledgement cannot acknowledge an attachment. Request correlation is exclusive, including rebuilt-upload aliases. Operation records contain identities, source revisions, document hashes and process-keyed commitments; they exclude answers, cookies, signed upload fields and tokens. The random commitment key is never persisted.

The existing attempt-wide crash fence remains authoritative. Per-operation acknowledgements help explain a live session; they do not authorize reopening an interrupted guest draft. A fresh render cannot prove ownership of the previous draft. Legacy, alias and unknown-outcome holds remain in place.

Public ATS submission APIs are employer integrations: [Greenhouse requires a Job Board API key](https://docs.greenhouse.io/job-board.html#authentication), [Ashby requires candidatesWrite](https://developers.ashbyhq.com/reference/applicationformsubmit), and [Lever requires an employer API key](https://github.com/lever/postings-api#application-api). These APIs do not provide a universal unauthenticated applicant submission route.

## CAPTCHA capability

Passive native verification and the single final-request guard remain unchanged. `human_verification_wait_seconds` starts at zero. A visible isolated browser is required to opt in. The optional `human_verification_handoff` setting also starts disabled and requires that bounded wait.

The loopback dashboard's existing host, origin and token checks protect `POST /api/human-verification`. Send `{"action":"claim"}` during the current challenge to obtain one short-lived controller token. Use that token in subsequent request bodies, never URLs. Heartbeat every five seconds with `{"action":"heartbeat","controller":"..."}`. A 20-second disconnect, the overall deadline, a worker crash, or a dispatched final request closes control. A second controller cannot take over or reclaim it.

The dashboard offers **Complete challenge here** during an opted-in wait. Its focused dialog shows only the challenge image, supports pointer selection by mouse or arrow keys and Enter, maintains the controller heartbeat, and ends the verification wait on close or connection loss. The attempt remains held for outcome review. Audio verification and local completion remain available in the same worker browser. Desktop notification delivery depends on the host's notification permissions.

For a trusted client, `frame` returns a cropped PNG of the challenge iframe. `click` accepts normalized `x` and `y` strictly between zero and one a one-use increasing `sequence`, starting at one, and the `frame_revision` returned with the image. A changed image or frame geometry rejects the selection and refreshes the image without repeating the click. Only the worker holding the existing isolated browser can execute the queued click, and it rechecks final-request dispatch first. `disconnect` ends the handoff.

The solver prototype is restricted to explicitly authorized loopback fixtures, disabled by default and disconnected from employer adapters. Providers receive only public fixture coordinates and bounded time/cost limits. Invalid, expired, unavailable and late results hold the fixture attempt; timed-out provider cost reservations remain held. No real vendor integration or employer acceptance is claimed. [2Captcha documents a vendor interface](https://2captcha.com/api-docs/recaptcha-v2), but its advertised capability is not evidence of employer acceptance or authorization. Any future integration needs site authorization and privacy review first. [Google requires reCAPTCHA response tokens to be single-use and verified within two minutes](https://developers.google.com/recaptcha/docs/verify). CAPTCHA completion is never an application receipt.

## Mail evidence and explicit retries

Company-scoped mail retrieval includes Spam and Trash without restricting receipt wording. Deterministic classification recognizes ordinary job-application and candidacy receipts plus reviewed Spanish, French and German phrases. Full role, seniority, year and location matching remain conservative. `gmail_confirmed_aliases` accepts only addresses explicitly confirmed by the applicant; none are inferred. Owner-forwarded receipts need an original recipient matching the owner or an explicitly confirmed alias and remain unverified review evidence.

Search and classifier revisions invalidate old scan completeness. Historical backfill is followed by a bounded overlapping catch-up before freshness can authorize work. Incomplete or malformed pages and unavailable authorization fail closed. [Gmail API search differs from Gmail UI search, including alias expansion](https://developers.google.com/workspace/gmail/api/guides/filtering).

The separate receipt correlator reads messages without sending, following links, changing outcomes or retrying applications. `hireme gmail receipt-candidates` reads one bounded page; pass its `next_page` through `--cursor` to continue. Owner recipient, an exact posting link and a plausible attempt window produce review candidates. No employer-specific auto-confirm rule has been independently commissioned, so automatic confirmation remains disabled. Sender claims and authentication headers alone are insufficient. Absence of mail never proves non-submission.

Explicit retries atomically retain the complete prior attempt in normal history and issue one authorization bound to its reconciled `not_submitted` outcome and exact approved package. If facts changed before the first retry approval, `retry-not-submitted` accepts an explicit `--approved-package` file while retaining the original attempt unchanged. An unused, unreserved approval can be replaced explicitly with `hireme renew-retry APPLICATION_ID --note "..." --approved-package /private/reviewed-package.json`; the supplied package must validate against current approved facts and documents. A reservation belongs to one live session, and interruption does not reopen it. Verification continuation remains limited to that live attempt; a new process cannot acquire an interrupted reservation. Restored unused authorizations are held. Unknown, confirmed and verification-pending outcomes cannot issue retry authority. Older retry events and superseded approval evidence remain intact.

## Gmail and backups

Read-only Gmail features require read permission. Sending reports additionally requires send permission; reconnect with reporting enabled to add it. Existing user-provided client and token files are preserved if reconnect fails. Incremental consent requests include already granted scopes. A Gmail API access check and the Google Cloud project's publishing status are separate evidence: client JSON and a successful refresh cannot establish whether a project is in Testing or Production.

[Google lists gmail.readonly as restricted](https://developers.google.com/workspace/gmail/api/auth/scopes). [External OAuth applications in Testing generally receive seven-day refresh tokens](https://developers.google.com/identity/protocols/oauth2#expiration); verification and security-assessment requirements depend on deployment and applicable exceptions. Check the actual project's consent configuration before claiming durable unattended operation.

The encrypted backup receiver can run on macOS or Linux and pull from any supported SSH worker, including a Pi. Existing SSH configurations keep their format. A local worker can instead use `source_root` with a user-selected mounted off-device destination. Replace `host`, `identity` and `ssh_binary` with that absolute source path; keep `age_identity`, `age_binary`, `destination`, `state_directory` and `recipient`. A local-source destination must already exist on a mounted filesystem other than the root or source filesystem; the agent will not create a missing mount point. A destination on the same filesystem is rejected. A separate filesystem is a local check, not proof of independent physical storage; the operator must choose an actual off-device mount.

Snapshots remain consistent and encrypted before publication. An independent decrypt/restore verifies integrity and referenced documents before atomic publication or retention. Restores start paused; credentials and live CAPTCHA control are excluded. Keep the newest two verified archives and apply the existing 14-day retention only after verification. `backup-agent install` uses a macOS LaunchAgent or a Linux cron entry; it preserves unrelated schedules. Linux cron monitoring records health in its private status file; desktop alerts additionally require an available graphical notification session.

Live commissioning requires a previously unattempted, duplicate-screened eligible posting and confirmed facts; an uncertain attempt remains held. Report the exact tested commit, local and hosted checks, isolated installation, disposable private-history upgrade/restore, independent public-code review, deployed revision and actual scheduler observation.
