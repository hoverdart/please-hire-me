# Application browser reliability

## Adaptive application execution — November 3–4, 2026

The deeper limitation was the executor, not just answer generation. The worker required a separately implemented backend protocol and verified flow for many application steps. An unfamiliar Workday tenant or a platform without installed native flow evidence stopped before it could use otherwise ordinary visible controls. Improving a generated answer could not repair that execution gap. OpenAI's [documented computer-use pattern](https://developers.openai.com/api/docs/guides/tools-computer-use) observes the environment, executes an action, and observes its result in an isolated session. This comparison concerns the public interaction pattern, not access to Codex's proprietary implementation.

`AdaptiveBrowser` now implements that loop in the local Python worker. It observes accessible controls, resolves values from existing confirmed sources, opens and searches custom choices, fills one control, reobserves conditional changes, adds confirmed history rows, attaches exact approved PDFs, advances saved steps, and verifies the final acknowledgement together with a fresh receipt. It retains its own persistent browser session throughout. Fixed native transports remain preferred where operational; fresh Workday jobs and unsupported native forms can use the UI strategy. Valid exact posting URLs admit additional Workday tenants without adding a hard-coded tenant entry. Saved native-only platform listings can use this strategy when the connection and automatic applications are explicitly enabled. Bulk discovery remains separately gated.

Workday's adaptive path verifies the rendered public requisition instead of requiring a separate urllib API read. This matters when Workday serves its ordinary browser client but rejects the discovery client's request. Same-shard `/wday/asset/` reads include fetched translation JSON; those files are needed to render the page. The executor waits for usable controls after navigation, recognizes provider-choice sign-in screens before password fields appear, and generates tailored resumes only after refreshing the posting. An untouched entry checkpoint re-enters through observed controls after authentication. Workday also re-enters an initialized client session when no answers, files or completed steps were saved; other employers retain acknowledged entry checkpoints. The dedicated NVIDIA login window checks all of its own tabs and retains session-only cookies only after its exact authenticated profile response verifies the confirmed owner, then closes itself.

Workday prompt inputs are recognized without an ARIA combobox role. Nested categories are expanded before resolving a leaf answer, options stay bound to their own widget, and selected chips are read separately from the search input. Stable field labels and wrapper identity survive re-renders. Confirmed institutions can be searched when a virtualized menu initially exposes only a few choices. Transparent native radios remain observable. Split phone controls preserve a confirmed national number; device type and an absent calling code require confirmation. Native form-definition POSTs with inspected context schemas remain reads and cannot authorize ordinary saves.

Saved Workday applications resume through the exact requisition's observed Candidate Home menu and Continue Application link. An expired owner session requests sign-in before that navigation. Prefilled employment and education rows bind to confirmed source identities rather than their displayed order; unknown or ambiguous rows remain held. The binding stays fixed while a row is edited. Current positions start without an obsolete end date, and observed Add Another controls create missing confirmed entries. Academic prompt searches use source-derived words while retaining the original approved claim. Reviewed academic option translations remain bound to the source record, revision, question and choices. Questionnaire legends take precedence over generic “Select One” accessibility labels. Before advancing, the executor rechecks the current values; bounded employer validation feedback identifies rejected saves. Identical revisited source assertions share one recovery step while each remote save keeps its own journal entry. Populated native disclosure, agreement, resume and self-identification definitions remain reads only with the exact definition header and bounded, observed context schemas. Workday's polite success announcement for an uploaded hash-named PDF is not a validation error; failed uploads and other alerts remain blocking.

Compound US EEO choices require both the confirmed race response and an explicit Hispanic/Latino response. Broader employer categories can represent explicitly confirmed regional identities; names, nationality and citizenship never establish a demographic answer. The employer-support question requires explicit work authorization, unrestricted authorization and sponsorship facts together. An application agreement approval is scoped to its job, wording and linked terms, including when an older employer-wide answer exists.

The model can choose only offered opaque action IDs. It receives observed headings, page text and action labels, which can include rendered applicant information. It has no browser connection, arbitrary selector, code-execution or request-authoring tools. Python owns all applicant values, actions, source validation, budgets, account checks, document hashes and final intent. Workday writes require an authenticated profile read matching the confirmed applicant. The dashboard's **Sign in to employer** action and existing CLI login open the worker's dedicated profile; they never attach to personal Chrome tabs. Login completion requests another identity check and does not itself grant write authority.

Each UI mutation has a durable operation intent before transmission. The router captures the exact upstream response before returning it to the page, with automatic request retries and redirect following disabled. This avoids losing a save acknowledgement when the website immediately navigates. Verified step positions and upload proofs survive restart independently of the prepared-package pointer. Adding an unrelated confirmed fact revalidates existing sources without losing the remote step. Changed source claims, unknown saves and uncertain final outcomes remain held. Local adaptive preparation sends no answers, saves or files; live multi-step saves require **Allow live application steps to save…** in Search & automation.

Synthetic real-browser tests exercise multi-step saves, debounced autosaves, conditional fields, nested and virtualized choices, selected chips, exact uploads, multipart submission, redirect receipts, checkpoint recovery, failed saves, source revocation, missing acknowledgements, invented model actions and isolation from unrelated browser tabs. An authenticated NVIDIA application completed My Information, My Experience, Application Questions, Voluntary Disclosures and Review after the applicant approved the required terms. The final UI displayed Application Submitted. A fresh, owner-authenticated record for the same application ID and requisition reported `draft=false` and Application Received. Independent reads also verified four employment entries, one education entry and the approved resume association. The first final run conservatively recorded an unknown outcome because its acknowledgement was not recognized; it was reconciled against that fresh employer evidence without another submission.

The executor now supports the same narrow Workday readback during final verification: all final-action requests must be acknowledged, the visible receipt must be new, the account owner must verify again, and the exact application referenced by the client's finalizer must report Application Received with matching role and requisition. A draft, wrong account, missing acknowledgement or unrelated receipt cannot confirm an application. This readback never retries a final request. The validator accepts the observed NVIDIA record; synthetic tests cover the transport and rejection conditions. Other Workday status wording remains conservative. Cross-origin application frames, CAPTCHA, unknown attestations, inaccessible widgets and existing platform-profile resumes whose exact contents cannot be verified can still require help.

## Browser inspection and routing — November 2, 2026

The app is not running the same general browser agent as an interactive Codex session. Its subscription CLIs have tools disabled; Python inspects fields and grants exact native requests. A new page shape, unrecognized button or unimplemented transport can stop that executor even when an interactive browser agent could complete the task. Handshake and Work at a Startup previously required native inspection, preparation, submission and verification capability before even checking whether a saved listing simply linked to an already supported ATS. No production native flow evidence is distributed, making that path unavailable by default.

The browser now follows observed Ashby/Lever application links bound to the exact saved requisition, including when the posting contains unrelated inputs. It uses direct navigation rather than remote click handlers. The managed model can choose only an observed approved navigation ID; it receives no arbitrary browser, code or shell capability. Applicant forms are distinguished from unrelated forms using their resume and identity controls. Hidden conditional controls no longer become questions, while hidden upload pickers in visible groups remain inspectable. Each filled parent field is followed by a fresh inspection before subsequent controls are used. One form retains its model connection across conditional refreshes. Validation targets the applicant form instead of every form on the page.

Individual saved platform listings now have an independent read-only external-routing operation in job details, the CLI and the authenticated API. It checks visible listing identity and a unique explicit requisition link at the same employer. It queues the employer job, preserves its platform origin, reuses existing ATS metadata and never records a submission from navigation. Prepared, attempted and archived application identities stay protected. Reimporting a routed listing reuses its canonical employer route. The platform's native application and automatic-search capability flags remain separate.

Configured Workday adapters now perform their own authenticated session checks without first requiring a redundant manual signed-in preference. The reviewed native driver registry, draft permission, owner-bound session and commissioning requirements remain enforced. Public read-only probes matched the existing posting-identity checks for the five configured tenants; these reads did not create drafts or submit applications.

Synthetic regressions cover navigation handlers, unrelated forms, hidden uploads, reused controls, exact platform/employer identities, paused inspection, routing idempotency, historical outcomes, native Workday session authority, API validation and desktop/mobile operation. These are local compatibility checks. Native-only Handshake and Work at a Startup submission, arbitrary Workday tenants, new ATS transport shapes, login and CAPTCHA remain outside this repair's verified support. No real application was submitted to validate these changes.

## Ashby and Lever audit — October 31–November 1, 2026

The primary application bottlenecks were a signed-out model connection, avoidable factual-answer lookups, and native form mismatches. Increasing the submission target alone did not resolve them.

## Repairs

- Codex structured output now omits the unsupported wire-level `uniqueItems` constraint while retaining the complete original schema for local validation. Unknown source IDs, duplicate citations and excess items remain invalid.
- A form shares its model connection across fields and cover letters. An unavailable or incompatible connection is checked once per configuration within that form rather than spending another request slot for every question.
- Source selection preserves the current approved resume before trimming supplementary context to the existing 24,000-character limit. Keyword-heavy context notes previously displaced resume dates and measured results. Independent grounding review and source hashes remain mandatory.
- Short descriptions of work or projects use the narrative writing-and-review loop. A rejected unsupported detail can be repaired and reviewed again before caching, rather than ending in an avoidable short-fact hold.
- Writing repairs reconsider unattempted mixed-form holds containing rejected writing. They leave ordinary missing-fact holds and uncertain applications closed.
- Observed university, return-offer year, internship start and local office questions use revision-bound confirmed facts. Country placeholders require validated employment-country context. A graduation date does not establish permanent employment availability or an exact start day.
- Direct graduate-study requirements such as “Ph.D. candidate working in” and “Current MS or PhD student or recent graduate” are screened before application browsing. Descriptions of graduate students mentoring interns remain distinct from applicant requirements.
- Model and browser changes can reconsider unattempted information and widget holds. Existing application history and uncertain guest drafts remain protected.
- Saving an employer-specific answer no longer releases unrelated employers' information holds. Relevant scoped answers and legacy host-wide answers still trigger reconsideration.
- An exact saved approval takes precedence over an older generated answer cache. Current-date enrollment and graduation confirmations remain derived from confirmed dates.
- Ashby's empty auxiliary resume-autofill picker is excluded from application questions. Named, required, populated and form-owned upload controls still require inspection.
- Ashby's native verification fingerprint accepts a bounded string up to 20,000 characters. The prior 2,000-character limit rejected a 3,810-character value from the official client, aborting the final request and producing a network-error message. Fingerprint and CAPTCHA contents stay out of diagnostics.
- Native Ashby dates convert an approved exact display date to the observed ISO calendar-date wire format before autosave authorization. Unknown formats, invalid dates and month-only values remain held. The display answer and its source remain unchanged, and the final grant still requires the exact native acknowledgement.
- A native single checkbox has one checked wire value and an unchecked absence. The planner and answer context now represent that encoding consistently.
- Lever permits exact descriptors for an entirely unanswered optional survey only after checking employer identity, template identity, optional fields, rendered choices and absence of responses. It does not generate demographic answers. Other survey shapes remain held.
- Lever location selection can make a second read-only lookup using the complete approved label. Selection still requires one exact suggestion and its matching native location object.
- Lever discovery and fresh posting inspection share the hosted page's HTML description fields. An inspected Summer 2027 posting retained Summer 2026 wording and a 2025 deadline in its stale API plain-text copy. Plain text remains a fallback when HTML is absent; an explicitly empty HTML field cannot resurrect removed content.
- Lever university widgets retain the validated visible Select2 proxy's named native select, requiredness and official options. Follow-up approvals bind to their native card field; a wrongly mandatory “Other” degree follow-up can say “Not applicable” only after an adjacent, confirmed non-Other degree choice in that same card.
- Duplicate unselected labels in a native select no longer block a uniquely approved label with a unique native value. Ambiguous selections, missing native mappings and duplicated selected IDs remain blocked.
- Explicit undergraduate and graduate transcript requests use the approved transcript document, including a request ending in a sentence period. Combined or unrelated document requests still cannot disclose it.
- Greenhouse's localized English race prompt retains its canonical field identity and approved answer. A standalone custom checkbox maps its approved checked state to the sole native option only when its current ID, name, type, value and option label match; it never creates consent or a demographic answer.

## Evidence and limits

Two real Ashby applications returned correlated native success acknowledgements and fresh completed-application receipts after the fingerprint fix. Another inspected Ashby attempt reached an applicant CAPTCHA and remains uncertain after its challenge wait expired. These observations validate the accepted forms, not every Ashby employer or conditional workflow.

Two real Greenhouse applications exercising the localized prompt and standalone checkbox paths also returned correlated native acknowledgements and fresh completed-application receipts after those repairs.

Lever's real Shield AI application passed complete field filling, document checks and native submission preflight after the university fixes, then reached an applicant CAPTCHA. Its bounded challenge wait expired without an acceptance receipt. Native transport also has synthetic coverage, but live acceptance remains unverified: another inspected form returned an employer verification error. These attempts remain uncertain; no receipt was invented and no uncertain application was retried.

A daily target is an operating setting, not an achieved submission count. Reaching 8–10 confirmed submissions per day still needs observation of normal scheduled runs with sufficient eligible openings and successful employer verification. CAPTCHA and applicant-only attestations can require human involvement. Unknown outcomes remain protected regardless of targets.

An ordinary six-hour Mac scheduled cycle completed after installation and recorded two confirmed applications. This is runtime evidence for that cycle; it does not establish a sustained daily rate or Lever acceptance.

The Mac installation and its private applicant workspace are separate from the source checkout and Raspberry Pi installation. Install the tested artifact before restoring the schedule. Use one active scheduler for the applicant and keep private receipts, logs, documents and backups outside Git.
